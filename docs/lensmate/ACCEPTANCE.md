## B17 — Local queue and deferred synchronization

Audit (before this item): no durable offline queue exists in `packages/core`. Existing pieces that are reused or referenced:

- `packages/core/src/retention.ts` — temporary-item expiry (24 h) and sweep; reused for the expiry rule.
- `packages/core/src/provider-gateway.ts` — retryable/non-retryable classification; the queue uses its own bounded backoff (same idea, separate concern).
- `apps/mobile/src/memory/native-store.ts` — phone-side encrypted SQLite store; not used by `packages/core` (core has no native imports). Its wiring to the queue is a later integration item.
- `apps/mobile/src/memory/backup.ts` — AES-GCM encryption on the phone; the queue takes an injected cipher with the same shape instead of importing it.

Implementation: `packages/core/src/offline-sync-queue.ts`, tests in `packages/core/src/offline-sync-queue.test.ts`. No network, phone, or cloud import. Time is injected (`nowMs`), so tests are deterministic.

Design summary: the queue persists a whole snapshot through an injected `QueueStorage` (atomic save), serializes operations, and keeps memory unchanged when a save fails.

## B19 — Network loss recovery and automatic reconnection

Audit (before this item): `packages/core/src/glasses-link.ts` defines connect/disconnect but no reconnection. `packages/core/src/broker-client.ts` maps failures to retryable codes but has no network-state tracking or reconnect loop. No existing module reports network state or schedules recovery. The new module is `packages/core/src/network-recovery.ts`. It is pure: the platform reports network state, and timers and randomness are injected, so tests are deterministic.

| #   | Criterion                                                                                                                                                                                                                                    | Test                                                                                                          |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 1   | Repeated network reports with the same value are ignored; a change is applied once                                                                                                                                                           | "ignores repeated network reports"                                                                            |
| 2   | Going online starts a stability window; if the network drops inside the window, no attempt is made (flap debounce)                                                                                                                           | "flap inside stability window makes no attempt"                                                               |
| 3   | While offline, no connect attempt is ever made                                                                                                                                                                                               | "no attempt while offline"                                                                                    |
| 4   | Failed attempts back off exponentially, capped at maxDelayMs; jitter adds at most jitterRatio of the delay                                                                                                                                   | "exponential backoff with cap and bounded jitter"                                                             |
| 5   | A successful connect resets the failure count; the next outage starts again at the base delay                                                                                                                                                | "success resets backoff"                                                                                      |
| 6   | Network returning (after the stability window) triggers an immediate attempt and cancels any pending backoff timer                                                                                                                           | "return online retries immediately"                                                                           |
| 7   | Going offline during an attempt aborts it; the aborted attempt is not counted as a failure                                                                                                                                                   | "offline aborts in-flight attempt without counting failure"                                                   |

## B20 — Local clock and timestamp continuity

Audit (before this item): `packages/core` has no clock abstraction. Core modules (queue, retention, router) take an injected `nowMs`. Mobile and broker code call `Date.now()` directly (for example `apps/mobile/src/memory/vault.ts`, `services/broker/src/server.ts`). Nothing measures monotonic elapsed time, detects wall-clock jumps, or orders events across restarts. The new module is `packages/core/src/local-clock.ts`. It is pure: the platform supplies wall time, monotonic time and a boot identifier, so tests use injected clocks.

| #   | Criterion                                                                                                                                                                                                                           | Test                                                                                         |

## B21 — Remote device lock and credential revocation

Audit (before this item): `services/broker/src/devices.ts` already provides per-device credentials stored as SHA-256 hashes, constant-time comparison, single-use enrolment codes that expire after ten minutes, and a `revoked` flag checked on every request through `authenticateDevice` (fail closed). `services/broker/src/server.ts` and `routes/usage.ts` use it. Missing for B21: no reversible device lock (distinct from revocation), no replay or staleness check on owner commands, no lock state that the glasses or app enforce offline, and no audit record of lock and revoke events. `packages/core` has no lock state machine. The new module is `packages/core/src/device-lock.ts`. It is pure: the caller authenticates the command and supplies the time.

## B22 — Factory reset and secure data erasure

Audit (before this item): `apps/mobile/src/memory/vault.ts` has `deleteItem` and `deleteAll` (clears the item store and the key). `apps/mobile/src/memory/native-store.ts` enables `PRAGMA secure_delete` and its "delete everything" path removes the database file and the key. `apps/mobile/src/memory/backup.ts` has `deleteBackup`. The broker `devices.ts` revokes credentials (B21 audit). Missing: one ordered reset that persists progress, resumes after restart, verifies erasure before reporting completion, and avoids any false "complete" claim while offline. The new module is `packages/core/src/factory-reset.ts`. It is pure: each erasure step is an injected function supplied by the platform adapter.

Ordered steps: (1) lock local credentials, (2) erase local data, (3) delete backups, (4) revoke remote credentials, (5) verify erasure. Remote revocation can be pending while offline.

## B25 — Optional phone, PC and accessory pairing

Audit (before this item): `packages/core/src/glasses-link.ts` defines only the transport interface (connect, disconnect, send, subscribe). `services/broker/src/devices.ts` enrols phone credentials for the broker (B21 audit). `apps/mobile/src/ai/connection.ts` manages the phone's broker connection. No module pairs an optional peer (phone, PC or accessory) to the glasses, confirms pairing with the owner, limits what a paired peer may do, or removes a pairing. The new module is `packages/core/src/pairing.ts`. It is pure: the platform supplies the time, the confirmation code and the transport, so tests are deterministic. The glasses work standalone with no peer.

| #   | Criterion                                                                                                                                                                                                                                                           | Test                                                                                                                     |

| 1   | With zero peers the glasses remain fully usable: standaloneAllowed is always true and no peer is required for any standalone action                                                                                                                                 | "standalone operation needs no peer"                                                                                     |
